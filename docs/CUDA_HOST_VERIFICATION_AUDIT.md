## 1. Did all mandatory tests pass?

**NO on the audit host; PENDING on a CUDA + OptiX-SDK host.**

The committed `docs/CUDA_HOST_VERIFICATION_REPORT.md`
(generated by `tools/verify_cuda_host.py` per CUDA-H.9)
records the audit-host's empirical outcome:

```
overall : REPAIR
pass    : 1
fail    : 9
skipped : 3
```

The 1 pass is `device-info` (CPU-only diagnostic; doesn't
require CUDA). The 9 failures are the nine mandatory CUDA
render commands hitting their documented "requires CUDA"
audit-host fallback. The 3 skipped entries are the OptiX
commands deferred per CUDA-H.8 because the operator did
not pass `--optix` (skipped is non-failure for the runner's
exit code).

Per the CUDA_HOST_VERIFICATION_PLAN's PASS criteria (§5),
a verification PASSES only when every command in the
active set passes. The audit-host run does not meet this
bar, but that is the documented runtime-deferred posture
every prior Stage 13/14/15/19/20/21 audit predicted: the
audit host has no CUDA toolkit (`which nvcc` returns
nothing) and no OptiX SDK (no `optix.h` under `/opt`,
`/usr/local`, or `$HOME`).

A future operator run on a CUDA + OptiX-SDK host is
expected to flip every CUDA failure to pass + (with
`--optix`) flip every OptiX skip to pass, producing an
overall `PASS` report. That report will replace the
currently-committed REPAIR report byte-for-byte (the
runner is deterministic per CUDA-H.9; the only varying
content is the per-test status, which is a function of
hardware + tree state).

## 3. Is the CUDA path production-usable?

**STRUCTURALLY YES; EMPIRICALLY DEFERRED.**

What every prior audit (Stage 6/9/11/13/14/15/19/21) has
confirmed structurally:

- Every CUDA-required `--render-*` dispatcher is wired
  end-to-end (parse -> upload -> kernel launch -> save).
- The audit-host fallback fires on demand and reports the
  documented "requires CUDA" error when CUDA is missing.
- The CUDA renderer has not regressed across any of the
  Stage 17-21 OptiX / denoiser arcs (proved by
  `git diff` showing zero bytes changed in `src/cuda/`,
  `src/renderer/`, `src/pathtracer/` across the entire
  Stage 20 + Stage 21 arc).
- All CUDA-side ctest targets (math_tests, image_tests,
  gpu_tests, pathtracer_tests, relativity_tests,
  demo_tests) remain 6/6 green in the audit-host OFF
  build; an additional `optix_tests` brings the
  ON-audit-host count to 7/7.

What is empirically deferred to a CUDA + OptiX-SDK host:

- The actual `cudaMemcpy` / kernel-launch / readback
  cycle for any of the nine CUDA commands listed in
  Question 2.
- The actual content of every `output/*.ppm` file
  (existence + size > 0 verified by the runner; PPM
  validity + visual fidelity require an operator with
  the right hardware).

Verdict for production usage: the CUDA path is built on
a stable foundation that has been incrementally verified
across 20+ stages, but the "production" claim requires
an operator run on a real CUDA host. The runner +
report infrastructure (CUDA-H.1..H.9) now makes that
verification a single command-line invocation. After
the first PASS report is committed, the CUDA path can
be claimed production-usable empirically rather than
structurally.

## 4. Is OptiX usable or partial?

**PARTIAL — usable for the verified subset; one
production gap remains.**

What is wired AND empirically usable on a CUDA +
OptiX-SDK host (per the post-Stage-20 + post-Stage-21
capstone audits):

- OptiX backend lifecycle (init / device context /
  shutdown) — Stage 12B / 17A.
- OptiX raygen + miss + closest-hit pipeline,
  triangle GAS, mesh GAS — Stages 17A / 20A..F.
- OptiX material + light + textured-material + shadow
  rays — Stages 20G / 20K / 20L / 20M.
- OptiX path tracer (spp + bounces) + accumulation —
  Stages 20I / 20J.
- OptiX AOVs (six PPMs) — Stage 20N.
- OptiX denoiser end-to-end via `OptixDenoiser::denoise`
  + `denoise_and_save_ppm` + `--render-optix-denoise`
  CLI — Stages 21B..21E.
- The CUDA-side `--render --denoise` flow that
  re-renders with AOVs and runs the OptiX denoiser
  on the result — Stage 21E.2.

What remains as a known polish gap:

- **OptiX Gap A** (durable AOV ownership for the OptiX
  path's `render_aovs`): the `OptixRenderer::render_aovs`
  entry frees its AOV device buffers before returning,
  so the OptiX-rendered AOVs cannot feed the OptiX
  denoiser directly. The Stage 21E.2 dispatcher works
  around this by re-rendering through the CUDA AOV
  pipeline when `--denoise` is set, even when the
  user's primary render came through the OptiX path.
- Gap A's first slice (Step 1 of 5: types +
  declaration) shipped at commit `6287471`; Steps
  2..5 (SDK_FOUND body, consumer wiring, CLI surface,
  capstone audit) remain per
  `docs/OPTIX_GAP_A_POLISH_PLAN.md`.

OptiX is usable today for every entry the CUDA-H.x
runner verifies; the open gap is a polish item for the
OptiX-side AOV-feeds-denoiser path, not a production
blocker for the existing CLI surfaces.
